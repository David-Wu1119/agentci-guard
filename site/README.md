# AgentCI Guard research site

This directory builds the static [cryptoaxiom.net](https://cryptoaxiom.net/) site. In this source version, the hero card is a schematic review checklist, not executable YAML or scanner output. The page explains the experimental scanner, replays the `event-gated-prt` synthetic fixture from public commit `5c045e0469f412aecd0f9d5f32876bf10c7fc66b`, and offers a browser-local scan of one GitHub Actions YAML file. It does not measure precision or recall, connect to GitHub, or execute the workflow.

The browser scan uses the same `parseWorkflowFile` and `scanWorkflowFiles` core as the CLI, bundled into a content-addressed `scanner-browser.<sha256>.js` file. The result renderer is also content-addressed as `app.<sha256>.js`. This source checkout is an unreleased browser candidate, not the published `v0.6.2` Action/CLI. Results show the page-build source; the script URLs and Subresource Integrity (SRI) bind the browser scanner and renderer bytes to that page, but do not establish that the source was published or that accuracy was measured. Compare browser and published Action/CLI behavior separately. Pasted text and chosen files stay in the browser; they are not uploaded. Replacing a nonempty draft with the sample or a selected file requires confirmation; edits clear stale file selections. Results identify the sample, uploaded filename, or pasted YAML, but use the virtual path `.github/workflows/input.yml` rather than the uploaded file's real path. Input is capped at 250,000 characters, or 250,000 bytes for a selected file, and 500 steps across all jobs. The browser wrapper rejects obvious malformed structure but is not a GitHub Actions schema validator. Repository config and other local reusable workflow files are unavailable to this one-file scan, so a complete repository review still needs the CLI or GitHub Action. The page displays recognized agent-use steps separately from findings and diagnostics; zero recognized steps does not prove no agent exists. Always read `diagnostics` and `analysis_complete`; zero findings and `analysis_complete=true` do not prove safety, because indirect tool fetches can escape the static model.

From the repository root, run `pnpm site:check`. This builds the scanner and the six allowlisted site assets, verifies the browser bundle against the scanner on adversarial fixtures, and writes `site/BUILD_MANIFEST.json` with SHA-256 hashes. CSS retains a content-hash query string; both JavaScript files use SHA-256 filenames plus SRI, so cached HTML cannot silently load newer scanner or renderer bytes under an old page-source label. If a previously cached page points to a script asset no longer served, scanning stops; a missing scanner shows a refresh instruction, while a missing renderer leaves scan controls disabled with a static refresh instruction. Cached HTML cannot be changed retroactively; affected visitors must refresh. The same-origin Content Security Policy remains in place. Beside scan results, a Build provenance disclosure contains the browser bundle SHA-256 and, only for a clean Git checkout, links its source commit. A dirty or non-Git build is marked without a commit link. The build alone does not verify that the commit is published; the production preflight does. These values do not measure accuracy. The assets are `index.html`, `styles.css`, `app.<sha256>.js`, `scanner-browser.<sha256>.js`, `_headers`, and `THIRD_PARTY_LICENSES.txt`. No extra browser dependency or hosted API is used.

CI runs the rendered check in isolated headless Chrome. Locally, start Chrome or Chromium in an isolated profile with DevTools on port 9337, then run `node site/render-check.mjs`. The check serves the five public assets over loopback HTTP so the browser enforces SRI, including negative tests with tampered scanner and renderer bytes. It also covers the real sample scan, malformed/non-workflow/empty/oversized inputs, local file loading, keyboard focus, the schematic hero card, anchors, five viewport widths, console exceptions, and external requests. It writes ignored screenshots and `site/VISUAL_CHECKS.json`. The loopback check does not apply Cloudflare response headers; verify those on the live deployment separately.

The previous informational deployment `a145c82a-bdbc-4333-9d31-58dd85567830` remains a rollback target. The deployment preceded source publication; an outsider needs a public ref to that exact commit to reproduce its bytes. The v3 benchmark remains development-only without human labels. A fresh repository-disjoint evaluation is required before any precision or recall claim.

After `pnpm site:check`, run `node site/check-live-deployment.mjs` to compare the five served files, including the content-versioned CSS and JavaScript URLs used by the page, and effective `_headers` directives with `https://cryptoaxiom.net/`. An optional base URL can check a specific Pages deployment instead: `node site/check-live-deployment.mjs https://<deployment>.axiom-console.pages.dev/`. This read-only gate fails when production still serves an older build; matching bytes do not establish that the source commit is public or that scanner accuracy is measured.

For a production release, first merge the reviewed source to public `main`. From a clean checkout of that exact commit, run `pnpm site:deploy`. Its preflight requires `HEAD` to equal the public `main` ref, runs a fresh `site:check`, verifies the worktree is still clean, and compares all six output files with the new build manifest before invoking Cloudflare Wrangler. Run `pnpm site:deploy-preflight` alone to test readiness without deploying. After deployment, run `node site/check-live-deployment.mjs` and record the Cloudflare deployment ID and hashes; a successful Wrangler command alone does not prove what production serves. The preflight does not prove scanner accuracy and cannot prevent a separate, direct Wrangler invocation or edits made between its check and deployment.
