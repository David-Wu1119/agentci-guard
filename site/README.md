# AgentCI Guard research site

This directory builds the static [cryptoaxiom.net](https://cryptoaxiom.net/) site. In this source version, the hero card is a schematic review checklist, not executable YAML or scanner output. The page explains the experimental scanner, replays the `event-gated-prt` synthetic fixture from public commit `5c045e0469f412aecd0f9d5f32876bf10c7fc66b`, and offers a browser-local scan of one GitHub Actions YAML file. It does not measure precision or recall, connect to GitHub, or execute the workflow.

The browser scan uses the same `parseWorkflowFile` and `scanWorkflowFiles` core as the CLI, bundled into `scanner-browser.js`. Pasted text and chosen files stay in the browser; they are not uploaded. Input is capped at 250,000 characters, or 250,000 bytes for a selected file, and 500 steps across all jobs. Results use the virtual path `.github/workflows/input.yml`. The browser wrapper rejects obvious malformed structure but is not a GitHub Actions schema validator. Repository config and other local reusable workflow files are unavailable to this one-file scan, so a complete repository review still needs the CLI or GitHub Action. Always read `diagnostics` and `analysis_complete`; zero findings and `analysis_complete=true` do not prove safety, because indirect tool fetches can escape the static model.

From the repository root, run `pnpm site:check`. This builds the scanner and the six allowlisted site assets, verifies the browser bundle against the scanner on adversarial fixtures, and writes `site/BUILD_MANIFEST.json` with SHA-256 hashes. The page displays the exact browser-scanner bundle SHA-256 beside scan results and uses it as script integrity; this identifies the running bundle bytes, not a published source commit. The assets are `index.html`, `styles.css`, `app.js`, `scanner-browser.js`, `_headers`, and `THIRD_PARTY_LICENSES.txt`. No extra browser dependency or hosted API is used.

For the rendered check, start Chrome or Chromium in an isolated profile with DevTools on local port 9337 and `--allow-file-access-from-files`, then run `node site/render-check.mjs`. The file-access flag is needed for the integrity-checked local script; do not use that profile for normal browsing. The check covers the real sample scan, malformed/non-workflow/empty/oversized inputs, local file loading, keyboard focus, the schematic hero card, anchors, five viewport widths, console exceptions, and external requests. It writes ignored screenshots and `site/VISUAL_CHECKS.json`. The local `file://` check does not apply Cloudflare response headers; verify those on the live deployment separately.

The interactive page was deployed to production on 2026-10-11 as Cloudflare Pages deployment `dcec7408-ccaa-4f35-be0c-272b5142f0c4` from commit `102cc92a0a24e69c67acf95c03dd2a98c97fca23`. See [the deployment receipt](DEPLOYMENT_RESULT_2026-10-11_BROWSER_SCAN.md) for asset hashes and live checks. The previous informational deployment `a145c82a-bdbc-4333-9d31-58dd85567830` remains a rollback target. The deployment preceded source publication; an outsider needs a public ref to that exact commit to reproduce its bytes. The v3 benchmark remains development-only without human labels. A fresh repository-disjoint evaluation is required before any precision or recall claim.

After `pnpm site:check`, run `node site/check-live-deployment.mjs` to compare the five served files and effective `_headers` directives with `https://cryptoaxiom.net/`. An optional base URL can check an immutable Pages deployment instead: `node site/check-live-deployment.mjs https://<deployment>.axiom-console.pages.dev/`. This read-only gate fails when production still serves an older build; matching bytes do not establish that the source commit is public or that scanner accuracy is measured.

For a production release, first merge the reviewed source to public `main`. From a clean checkout of that exact commit, run `pnpm site:deploy`. Its preflight requires `HEAD` to equal the public `main` ref, runs a fresh `site:check`, verifies the worktree is still clean, and compares all six output files with the new build manifest before invoking Cloudflare Wrangler. Run `pnpm site:deploy-preflight` alone to test readiness without deploying. After deployment, run `node site/check-live-deployment.mjs` and record the Cloudflare deployment ID and hashes; a successful Wrangler command alone does not prove what production serves. The preflight does not prove scanner accuracy and cannot prevent a separate, direct Wrangler invocation or edits made between its check and deployment.
